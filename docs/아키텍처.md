# 아키텍처

LINK-Radar 전체 구성과 데이터 흐름입니다. 만든 순서와 남은 일은 [개발 과정](개발_과정.md)에 있습니다.

## 1. 전체 구성

```mermaid
flowchart LR
    subgraph RAW["원본 (레포에 없음)"]
        T["SK 통신"]
        K["신한카드"]
    end
    subgraph EXT["외부 공공데이터 (external/)"]
        R["주민등록"]
        SL["시민생활 (강남)"]
        WX["기상청 ASOS"]
        RS["복지자원 원장"]
    end
    T --> ING["정리·적재<br/>bigcontest.ingest"]
    K --> ING
    ING --> INT["data/interim/*.parquet"]
    INT -->|"읽기만 · 파일 해시가 스냅샷 id"| AG["에이전트<br/>agent/ (LangGraph)<br/>신호·모델·규칙 도구"]
    EXT -->|읽기만| AG
    API["FastAPI<br/>api/"] <--> AG
    API <--> DB["SQLite<br/>실행·승인·가린 메모·체크포인트"]
    AG --> LLM["Gemini API (무료 등급)<br/>(질문 해석·추가 조사 선택·설명 문장)"]
    WEB["React 대시보드<br/>web/"] <-->|HTTP| API
```

**원칙**
- 분석 데이터(`data/interim` 등)는 적재 명령만 씁니다. API·에이전트는 이 파일을 읽기만 합니다.
- **지금 실제 동작**: 실제 그래프의 스냅샷 id는 dev 파일(`data/interim`·`external`·`ref`)의 해시입니다. 실행은 시작할 때 id를 고정하고, 도구가 매번 해시를 다시 확인해 파일이 바뀌면 `SNAPSHOT_MISMATCH`로 멈춥니다(조용히 새 자료를 읽지 않음). 발행 스냅샷 폴더(`data/snapshots/<id>/`, `bigcontest.snapshot`)를 만드는 코드는 있지만 도구는 아직 그 폴더를 읽지 않습니다. 그래서 파일이 바뀐 뒤 오래 멈춰 있던 실행은 이어 갈 수 없고 새 실행이 필요합니다([데이터 모델](데이터_모델.md) 운영 메모).
- 실행 상태(SQLite)는 FastAPI만 씁니다. 화면은 API만 부릅니다.
- 등급과 후보는 코드가 정하고, LLM은 질문 해석·추가 조사 선택·설명 문장만 맡습니다.

## 4. 데이터 흐름

### 4.1 배치 (정리 → 적재)

1. `bigcontest.ingest`: 원본 zip을 읽어 중복 제거, 강남·춘천만 남기고 Parquet로 저장 (`data/interim/`). 지금은 고정 기간(2025-07~12) 전체를 다시 만들어 덮어씁니다
2. 신호·모델·규칙은 **배치로 미리 계산하지 않습니다.** 실행(질의응답·조사·정기 감시) 때 그래프 안의 도구가 `data/interim`과 `external`을 읽어 계산합니다. 기준일보다 뒤의 자료는 쓰지 않고, 등급에는 `rule_id`·`rule_version`을 남깁니다
3. 스냅샷 발행 코드(`bigcontest.snapshot`: 새 폴더 + 검증 + `active.json` 교체)는 있지만 아직 도구가 발행 폴더를 읽지 않습니다(§1 원칙의 "지금 실제 동작")

### 4.2 질의응답 실행 1건

1. 담당자가 화면에서 질문 → `POST /runs` → 202 + `run_id`
2. API가 활성 `snapshot_id`를 실행에 고정하고 에이전트 실행 시작
3. 에이전트: 요청 정규화 → 질문 분류 → 계약 검사 → 근거 수집(필수 도구는 항상) → 후보 종류 → 반증(이탈 후보만, 후보별) → 신호 Guard → 등급(후보별) → 검토 배정 → 자원 매칭 → 근거 카드 → 보고서 → 보고서 Guard. 자세한 그래프는 [에이전트 설계 §4](에이전트_설계.md#4-그래프)
4. 승인 대기(`interrupt`): 상태를 SQLite 체크포인터에 저장
5. 화면이 `GET /runs/{id}`로 상태 조회 → 근거 카드 먼저 표시, 검사가 끝난 설명 문장 표시
6. 담당자가 근거 확인·자원 판정·메모 저장(`POST /runs/{id}/review`) → 바뀌면 보고서 다시 생성
7. 승인(`POST /runs/{id}/approve`, `report_revision` 포함) → 확정 기록 1건

### 4.3 정기 감시

1. 기준일 선택(과거 재생). 정기 실행 예약(스케줄러)은 없고, 현황·지도·후보 목록 화면 요청이 그 기준일 실행이 없을 때 한 번 만듭니다
2. 트리거(연휴 D-7, 폭염일·한파·폭우·폭설은 ASOS 일자료로 근사, 동절기) 계산 → 예정된 점검 후보 생성 (같은 사건은 한 번만). 폭염 **예보** 기록은 없어 과거 재생에서는 "확인 필요"로 둡니다
3. 이탈 경보 → 반증 → 예상 밖 이탈 후보
4. 등급 → 검토 배정(K) → 보고서 Guard → 후보 목록 발행 → 현황 화면. 승인은 담당자가 후보를 열어 조사할 때 받음

## 5. 오류·재시도

| 위치 | 정책 |
|---|---|
| 적재·스냅샷 | 적재 월 목록의 중복·빈틈은 거절(`check_new_months`). 하지만 `ingest` 실행은 고정 기간 전체를 다시 만들어 덮어씁니다(월 단위 추가 적재·재적재 거절은 아직 없음). 스냅샷 발행은 검증 실패 시 이전 스냅샷 유지 |
| 도구 | 오류와 빈 결과를 구분. 필수 근거 오류는 판단 보류 |
| LLM | 1회 재시도 후 규칙 기반·템플릿으로 대신. 실행당 호출 수·비용 한도(`configs/llm.yaml` `budget`)를 넘어도 템플릿으로 대신 |
| Guard | REVISE 최대 2회, 넘으면 ABSTAIN |
| 외부 수집 | 실패 시 이전 값 유지, 수집 기록 남김 |
| API | 오류 코드와 사유만 응답 |

## 6. 설정과 보안

- 키는 `.env`(커밋 안 함)에 둡니다: `GEMINI_API_KEY`, `DATA_GO_KR_API_KEY`. 필요한 이름은 `.env.example`에 있습니다.
- 원본 제공 데이터(`*.zip`, `data/`)는 레포에 올리지 않습니다. 원본 위치는 `configs/project.yaml`의 `raw_dir`(기본 `data/raw`) 또는 환경 변수 `BC_RAW_DIR`.
- API의 CORS는 화면 주소만 허용합니다.
- 인증은 토큰(역할 조회 < 검토 < 승인). 실행·질의응답·이어 묻기는 검토 이상이고 사용자마다 횟수 한도가 있습니다. 화면 빌드에 넣는 `VITE_API_TOKEN`은 누구나 볼 수 있으므로 조회 역할 공용 토큰만 넣고, 운영에서는 앞단 프록시에서 기관 로그인을 거치게 합니다([API 명세](API_명세.md) §1).
- 질문·검토 메모·승인 메모는 저장하기 전에 개인정보(전화번호·주민번호·이메일·상세 주소·이름+호칭)를 가립니다. 원문은 API 표·그래프 체크포인트·로그 어디에도 남기지 않습니다. 가린 글도 보존 기한(기본 365일)이 지나면 `uv run python -m api.retention --db <경로>`로 비웁니다.
- 화면과 보고서에는 항상 "개인 판정 아님 · 최종 판단은 담당자"를 표시합니다.

## 7. 실행 방법

```bash
uv sync
uv run python -m bigcontest.ingest      # 원본 → data/interim
uv run python notebooks/eda1_data_quality.py   # 리포트 다시 만들기 (notebooks/*.py)
uv run python -m bigcontest.weather     # 기상청 ASOS 다시 받기 (키 필요)
uv run pytest
```

API·화면 실행은 [README 실행·재현·문서](../README.md#run)에 있습니다.
